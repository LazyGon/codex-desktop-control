# 画像履歴による Bad Request の復旧

既存のシステムエラー復旧ワーカーが、原因を確認した特定の失敗ターンだけを修復する。新しい常駐プロセスや監視タスクは作らない。

通常の `serverOverloaded` などのキャパシティ不足は従来の再開経路を通る。画像の存在、枚数、Bad Request というエラーだけでは履歴を書き換えない。診断した担当者が、根拠ファイルとともに正確なタスクID・失敗ターンIDを確認登録する。過去の診断は別の失敗ターンへ引き継がない。

## 設定と実行

既存の復旧 `config.json` で `imageHistoryRepair: true` を設定する。既存の `enabled`、除外タスク、利用上限、購入クレジットの利用許可は引き続き適用する。

画像履歴が原因と確認できた後、通常権限の Node で実行する。`--evidence` は診断根拠を保存したローカルファイルであり、そのハッシュを記録する。認証情報や画像データを引数に渡さない。

```powershell
node control/image-history-repair-cli.mjs confirm --thread <タスクID> --failed-turn <失敗ターンID> --evidence <根拠ファイルの絶対パス> --confirmed-image-cause
node control/system-error-recovery.mjs dry-run
node control/system-error-recovery.mjs run
```

通常は既存の一分ごとの起動が処理する。手動起動も同じワーカーを使用する。配布版や別の状態ディレクトリでは、各コマンドへ `--directory <既存復旧状態ディレクトリ>` を追加する。配布版では既存設定の `sharedStatePath` が正準ランチャー状態を指している必要がある。

`confirm` は診断の記録であり、画像が原因かを推測して認定する機能ではない。原因が不明な400、認証・設定不備、キャパシティ不足に対して登録しない。確認登録の際の `thread/resume` は元の設定を読み取るためだけに使い、作業ターンは開始しない。

## 処理と保持するもの

1. 同じ失敗ターン、所有者、設定、診断根拠、現在の停止・除外・利用上限を確認する。
2. 埋め込み画像の原本を状態ディレクトリ内の `image-history/images/<タスクID>/` へ保存する。同じ画像は内容ハッシュで共有する。
3. 元のJSONLとは別に候補を作る。`input_image` を絶対ファイルパス・MIME・SHA-256を含む `input_text` に置換する。他の文章や項目順は保持し、JSONオブジェクトの外側の空白で各LFレコードのバイト長を保つ。SQLiteの投影オフセットを変更しない。
4. 正準AppServerで対象だけを一時アーカイブし、アンロードを確認する。通常権限の非表示PowerShellで `File.Replace` を一回実行し、原本のバックアップとACLを保持する。SQLiteは書き換えない。
5. 同じタスクIDでアーカイブ解除・再読込し、設定と権限を照合する。公式のコンパクションが正常終了したことを確認してから、元の許可済み作業の再開を一回送る。再開の受付と、その後の作業完了は別の状態として扱う。

原画像と元の履歴は削除しない。空白を残すため履歴ファイルのディスク容量は減らない。目的はモデルへ渡る埋め込み画像をファイル参照へ変えること。画像そのものが必要になった時は、その参照から必要な分を読む。

検証済みの経路はWindowsのローカル履歴・通常の直接入力タスクで、ゴールがない場合。ゴール付きタスクは再読込に伴う自動開始との競合があり、この経路では修復しない。子タスクがある場合も、公式アーカイブが子へ波及するため処理しない。いずれも通常の復旧規則を緩める理由にはしない。

## 状態、停止、結果不明からの調査

確認登録は `image-history/confirmations/`、各処理は `image-history/operations/<エピソード>/operation.json` に保存する。埋め込み画像の位置と退避先は同じ処理記録のmanifestにある。バックアップの場所は置換結果の `backupPath` に残す。

```powershell
node control/image-history-repair-cli.mjs status --thread <タスクID> --failed-turn <失敗ターンID>
node control/image-history-repair-cli.mjs revoke --thread <タスクID> --failed-turn <失敗ターンID>
node control/system-error-recovery.mjs stop
```

`revoke` は当該失敗の確認を撤回する。`stop` は既存の復旧機能全体を無効化する。すでに送った操作は取り消さず、次の破壊的処理・圧縮・再開を止める。既に一時アーカイブが確定している場合、その解除だけを後始末として行う。

各mutationの前に状態を永続化する。アーカイブ、置換、コンパクション、再開の結果が不明なら同じエピソードを自動再送しない。journalを削除して強制再実行しない。正準AppServerの最新状態と置換結果・原本/適用後ハッシュを先に照合する。原本へ戻す必要がある場合も、対象が停止・アンロード済みであることを確認した個別の保守で行う。稼働中の履歴へバックアップを上書きしない。

この機能はローカル履歴形式を扱う保守処理であり、公式APIの画像削除機能ではない。形式が変わった場合、画像を参照に置換できなかった場合、参照文字列が元の画像オブジェクトより長い場合は候補を適用しない。原本と証拠を残して担当者へ戻す。
