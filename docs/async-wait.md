# 非同期待機と通知の参考手順

適用範囲のAGENTSにある必須原則を前提に、対象作業に必要な節だけ参照する。履歴や例は新しい権限・製品契約を追加しない。control相対pathは C:/Users/lazyg/Documents/ChatGPT/codex desktop control 基準。

### ウェイターの通知条件と通知期限（2026-11-20 利用者指定）

ウェイター・watcher・完了待ち・再開通知など、名称によらず待機後に知らせる処理へ適用する。通知については本項を下記の既存手順より優先する。

- **完了を検知する条件は、本当に待ちたい対象そのもの一つだけにする。** 対象に含まれない成功/PASS、成果物の完備、別タスクの終了、ACK、登録時のturn ID・発言数、goalやタスク状態の一致などを追加条件にしない。既存実装を変更する際も、待つ目的と無関係な条件・制約を取り除く。
- **通知は既定で有効にする。** 対象の通常所要時間と今回の状況から妥当な通知期限を決め、起算時点・具体的な期限・短い設定根拠を保存する。対象条件が成立したら速やかに通知し、未成立でも期限に達したら必ず未完了・失敗・確認不能などの実状態を通知する。条件未成立や読取失敗を理由に無期限で無通知にしない。
- **期限通知を、待機対象の完了判定やその確認処理から独立して動かす。** RPC・ファイル読取・子処理が固まっても期限通知が止まらない実装にし、既存の通知・Receiver・スケジューラ経路を再利用する。通知期限を対象処理の強制終了期限へ流用しない。端末停止・通知先不通などで配送できないときは未達を永続化し、復旧後に未送信分を通知する。
- **通知配送と作業の自動再開は分ける。** 最新のthread/turn/statusは配送先を選ぶために読み、自動再開不可やgoalの変更だけを理由に通知を抑止・失効させない。通知のために停止済みgoalを勝手に再開しない。利用者の明示的な通知停止・取消、元の権限と重複配送・UNKNOWN再送禁止を守り、これらに待つ目的と無関係な通知gateを付け足さない。

### 実行環境の欠落を最優先で復旧する

Codexのコマンド実行に必要な補助プログラムや依存ファイルが見つからないエラー（例: Windowsの`codex-windows-sandbox-setup.exe`）を見つけたら、作業を漫然と再試行せず、まず実行環境の復旧を優先する。自分のタスクだけでなく、共有AppServerのログなどで他タスクの同種エラーに気づいた場合も、影響範囲を確認して対応する。

- 正準状態から実行中の共有AppServer本体・バージョン・配置先を特定し、欠落ファイルと探索先を確認する。同じバージョンの正規インストール先にあるファイルを優先し、署名またはハッシュを確認してから必要な配置先へ導入する。出所不明のバイナリを取得・実行しない。
- 原因がランチャーの同梱ファイル漏れなら、現在の環境だけでなく次回起動・アプリ更新後にも再発しないよう、キャッシュ生成処理とテストも直す。導入後は小さな実コマンドで復旧を確認し、失敗するなら新しいエラーを切り分ける。
- 稼働中の共有AppServerやDesktop、別タスクを不用意に再起動・停止しない。再起動や管理者権限、セキュリティ境界の変更が本当に必要なら、影響と承認条件を先に確認する。欠落を理由にsandboxやapprovalを緩めない。安全に復旧できない場合は、根拠と阻害要因を明示する。

Codexタスクの作成・一覧・読み取り・再開・入力・steer・中断・状態確認など、タスクを操作する際は原則として、そのPCで稼働中の**共有AppServer**を使う。接続先は当該control utilityの`launcher/state/current.json`など正準状態から確認し、推測したendpointや別に起動したAppServerへ接続しない。操作対象のthread IDと現在のturn/statusを再読し、対象を明示して実行する。共有AppServerが使えない場合は、黙って別経路へ切り替えず、理由と代替手段を示す。

未完了の依頼について、外部処理・別タスク・レビュー・デプロイ・PCの復帰などの非同期イベントを待つために現在のターンを終える場合、単に「待ちます」と報告して放置してはならない。ターンを終える前に、**同じCodexタスクを再開させる実行可能な仕組み**を作成または既存の仕組みに登録し、動作と停止条件を確認する。タスク自体を完了扱い・アーカイブ扱いにはしない。

**原則:** 待機の成立条件や有効期限を、登録時点のターンIDやユーザーメッセージ数に結び付けない。途中で別の入力やターンが生じても、待機対象の外部イベントが未解決なら登録を維持する。通知時に共有AppServerで対象threadと最新のturn/statusを再読し、稼働中ならその正確なturnへ`turn/steer`、停止中なら同じthreadへ`turn/start`で一度だけ届ける。ターンIDは配送先の確認と記録に使い、待機条件の代わりにしない。

- **ゴール付きの完了待ち（2026-10-21 利用者指定）:** 利用者が外部処理の完了待ちと自動再開を指示した場合は、再開処理を先に稼働確認し、正準共有AppServerで同じゴールを`paused`にしてから応答を終える。この待機運用の指示は、待機中の一時停止と条件成立後の自動再開を含む。待機中も`active`のまま自動継続を空回りさせない。完了通知側は、保存した同じゴール・今回の一時停止状態が現在も有効であることを確認し、本文や予算を置換せず`status: active`へ戻してreadbackしてから、最新状態に応じて同じタスクを再開する。後からの利用者の停止・変更・取消、完了、予算制限は上書きしない。ゴールの停止だけで再開手段を失わせず、UNKNOWNは再送しない。上位の権限・停止条件を維持する。

- まず本当に待つ対象一つとその成立条件、正確なタスクID、確認手段、確認間隔または通知契機、妥当な通知期限を定義する。対象未成立・失敗・確認不能でも期限到達時に通知する。共有AppServerに接続するスクリプトを作成し、既存通知・Receiverまたはスケジューラ等から一回実行で起動する。長時間ターンを占有するだけのポーリングはしない。
- 再開スクリプトは状態を永続化し、対象IDと待機条件と現在のturnを共有AppServerで再読する。対象タスクに稼働中turnがあればその正確なturn IDへ`turn/steer`、idleなら同じthread IDへ`turn/start`を一度だけ配送する。`thread/resume`が必要な状態なら先に行う。多重起動、重複通知、古いイベント、同一条件での無限再試行を防ぐ。配送結果が不明なときは推測で再送せず、記録を残して安全に停止する。
- 元の権限・sandbox・workspace・model・Git状態と外部操作のexactly-once境界を維持する。待機を理由に承認、送信、レビュー、Product変更などの権限を拡張しない。資格情報・会話本文・署名付きURLをログやコマンドラインに残さない。
- 再開方法、登録先、次回確認条件、停止・解除方法を引継ぎに明記する。短い同期的なツール待ちや、既に結果が確定している処理には新しいwatcherを作らない。待機トリガーを安全に設置できない場合は、設置済みと装わず、具体的な阻害要因を報告する。

### 例: 長時間のローカルビルド・実サーバーテスト

GradleやPaperの初回セットアップのように時間がかかる処理を待つときは、以下を一つの実装例とする。これはPCが稼働している間のプロセス終了待ちであり、再起動後の自動復旧が必要なら別途スケジューラ等に登録する。

1. テストを独立したバックグラウンドプロセスとして起動し、標準出力と標準エラーを作業領域内のログへ保存する。Windowsの`Start-Process`を使う場合は`-WindowStyle Hidden`を指定する。正確なPIDと開始時刻、対象thread ID、登録時点のturn ID（診断用）、待機期限を状態ファイルへ記録する。ターンの交代を待機解除条件にせず、PIDの再利用も開始時刻で検出する。
2. watcherを一つ起動し、`Process.WaitForExit`などOSの終了待ち機能でそのプロセスの終了を待つ。終了または期限到達を通知契機にする。エージェントのターン内で短い間隔のポーリングを続けない。終了コードとログの場所を記録する。
3. watcherは配送前に共有AppServerの正準状態（例: control utilityの`launcher/state/current.json`）を確認する。control utilityが対象threadを`thread/resume`し、最新のturn一覧を読み、稼働中なら正確なturn IDを指定して`turn/steer`、idleなら同じthread IDで`turn/start`することを確認したうえで、明示したthread IDに一度だけ配送する。別のAppServerを起動しない。
4. 状態を`armed`→`ready`→`dispatching`→`delivered`のように永続化し、排他ロックと一意のマーカーで二重起動・二重配送を防ぐ。`dispatching`は送信前に書き、送信結果が不明なら再送しない。AppServerが使えない場合は失敗を記録し、勝手に別経路へ切り替えない。
5. ターンを終える前に、テストとwatcherの両プロセスが稼働し、状態ファイルとログが期待どおり作られたことを確認する。引継ぎには次の契機・期限・状態ファイル・停止方法を示す。中止時は記録したPIDと開始時刻を照合して両プロセスを停止し、状態を中止として記録する。

この例だけではPC再起動時にテストとwatcherが停止する。再起動後も再開させる必要がある依頼では、永続状態を再読する一回実行のwatcherをタスクスケジューラや既存Receiverへ登録し、復帰時に対象プロセスと待機条件を再検証する。登録できなければ、その制限を明記する。
